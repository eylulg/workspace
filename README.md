# Workspace

A keyboard first issue tracker in the spirit of Linear: teams, projects and issues with status, priority, labels, assignee, due date and a Markdown description, shown as a grouped list or a drag and drop board. It has a command palette, single key shortcuts, an activity log, undo on delete, and an interface in English, Turkish and German.

Visitors use a seeded demo workspace straight away: two teams, three projects and 60 issues with fictional content. No sign up.

## Features

- **Issues list** grouped by status, priority or assignee, sorted manually or by priority, last updated, last created or due date. Filters for status, priority, assignee, label and project plus a text search. Every view lives in the URL, so it can be shared, and can be saved by name to the sidebar.
- **Board** with one column per status. Cards move by mouse, touch or keyboard, and screen readers hear where the card is during the move.
- **Optimistic updates** for status, priority and assignee changes and for board moves: the UI changes immediately and rolls back with an explanation if the server refuses.
- **Issue page** with an inline title editor, a Markdown description with a preview tab, comments, and an activity log that records every change.
- **Create issue dialog** opened with `C` from anywhere, with every property and `Cmd`/`Ctrl` + `Enter` to submit.
- **Command palette** (`Cmd`/`Ctrl` + `K`) for navigation, actions (create, theme, language, reset) and issue search by title or identifier.
- **Projects** with progress (done out of total, leaving canceled issues out), counts per status, lead and target date.
- **Labels** shared across teams: create, rename, recolour and delete.
- **Undo** after deleting an issue, from the toast.
- **Languages:** English, Turkish and German, with dates and numbers formatted for the locale.
- **Light and dark mode** that follows the system until you choose, with no flash on load.
- Works from 375 px wide upwards.

## Keyboard shortcuts

| Keys               | Action                                           |
| ------------------ | ------------------------------------------------ |
| `Cmd`/`Ctrl` + `K` | Open the command palette                         |
| `C`                | Create an issue                                  |
| `?`                | Show all shortcuts                               |
| `/`                | Search issues                                    |
| `G` then `I`       | Go to issues                                     |
| `G` then `P`       | Go to projects                                   |
| `G` then `L`       | Go to labels                                     |
| `V`                | Switch between list and board                    |
| `J` / `K`          | Focus the next or previous issue                 |
| `S`                | Set the status of the focused or hovered issue   |
| `P`                | Set the priority of the focused or hovered issue |
| `A`                | Assign the focused or hovered issue              |
| `Space`, arrows    | On a board card handle: pick up, move, drop      |

## Architecture

```
src/
  app/[locale]/        routes: issues, issue/[identifier], projects, labels
  features/            client UI by feature (issues, board, palette, shortcuts, shell, ...)
  lib/                 pure logic shared by server and client: URL query, filters, sorting, optimistic reducer, zod schemas
  server/
    db/                Drizzle schema, client (PGlite or Postgres), seed
    actions/           Server Actions (issues, labels, saved views, demo reset)
    queries.ts         cached reads
    session.ts         the single place that decides who the viewer is
  i18n/                next-intl routing and request config
messages/              en.json, tr.json, de.json
drizzle/               SQL migrations generated by drizzle-kit
```

- **Next.js 16 App Router with Cache Components.** Pages are server components that read through `use cache` functions tagged per team (`team:<id>`) for issues and per workspace for teams, members, labels, projects and saved views. Every read is behind the session cookie, so nothing touches the database at build time and the static shell is prerendered.
- **Server Actions for every write.** Each action validates its input with zod, checks that every referenced member, project or label belongs to the viewer's workspace, writes in a transaction, records activity, and calls `updateTag` for the affected team so the next render reads fresh rows. Actions return `{ ok, data }` or `{ ok: false, error }`, where the error is a message key the UI translates.
- **Optimistic UI.** The issues view and the issue page hold the server list in `useOptimistic`. A status, priority or assignee change, or a board move, is applied locally inside a transition while the action runs; when it settles the server render takes over, or the change rolls back and a toast explains why. Board order uses fractional sort keys, so a move updates one row.
- **One database schema, two drivers.** Drizzle defines a Postgres schema and drizzle-kit generates one set of migrations. Without `DATABASE_URL` the app runs on [PGlite](https://pglite.dev), Postgres compiled to WebAssembly, which migrates itself on first start, so local development, tests and the end to end suite need no database server. With `DATABASE_URL` it uses the `postgres` driver (Neon in production).
- **Sessions.** There is no sign in. The proxy (`src/proxy.ts`) gives each browser a random guest cookie, and `getViewer()` in `src/server/session.ts` turns it into a private copy of the demo workspace: the first request seeds a copy under the slug `visitor-<cookie>`, and after 24 hours the next request replaces it with a fresh one. Nothing a visitor types reaches anyone else. The nightly cron (`/api/cron/cleanup-demo`) deletes copies nobody came back to. Writes are limited to 40 a minute per visitor (in the memory of one server instance, enough to stop a script, not a security boundary), titles to 120 characters without a word longer than 60, descriptions to 5,000, comments to 2,000, and a copy holds at most 150 issues, 30 labels and 20 saved views. `getViewer()` is the only place that maps a request to a member; adding Auth.js means reading `auth()` there and mapping the user to their member row. Nothing else changes.
- **Not found.** Pages stream, so a missing page would answer 200. The proxy rejects unknown paths and missing issues (it asks `/api/issue-exists`, which reads the visitor's own copy) and answers a real 404 with `app/global-not-found.tsx`.
- **Analytics.** `src/features/analytics` loads `posthog-js` only when `NEXT_PUBLIC_POSTHOG_KEY` is set and captures `issue_created`, `status_changed` and `palette_opened`. Without the key nothing is downloaded.
- **UI.** The shared [`@eylulg/ui`](https://github.com/eylulg/ui) design system with its `workspace` theme variant and app chrome (top bar, sidebar, project switcher, theme toggle, footer), built on React Aria and Tailwind CSS 4. dnd-kit handles drag and drop. The command palette is the library one, with nested pages for the `S`, `P` and `A` shortcuts (status, priority or assignee of the focused issue).

## Internationalisation

[next-intl](https://next-intl.dev) with the locale in the URL (`/en`, `/tr`, `/de`). Every UI string is in `messages/*.json`, with ICU plurals where the count changes the grammar. The language switcher in the sidebar and the palette keep the current page and filters. A Vitest check fails when a locale is missing a key, has an extra one, or uses different message arguments than English. React Aria's own strings follow the page locale too.

## Run it

Requires Node 24. The app depends on the component library as `file:../ui`, installed as a copy with `npm install ../ui --install-links` (run `npm run relink` after rebuilding the library), so clone [`eylulg/ui`](https://github.com/eylulg/ui) next to this folder and build it once:

```bash
git clone https://github.com/eylulg/ui ../ui
(cd ../ui && npm install && npm run build)
```

Then:

```bash
npm install
npm run dev          # http://localhost:3000, data in ./.pglite
```

The first request creates the PGlite database in `.pglite`, applies the migrations; each visitor gets their copy of the demo on their first request. Delete the folder to start over, or use "Reset demo" in the sidebar, which resets only your own copy.

| Script                | What it does                                                  |
| --------------------- | ------------------------------------------------------------- |
| `npm run db:generate` | Generate a migration after changing `src/server/db/schema.ts` |
| `npm run db:migrate`  | Apply migrations to `DATABASE_URL`, or to PGlite without it   |

PGlite allows one process at a time, so stop the dev server before running `db:migrate` against the local database.

## Tests and checks

```bash
npm run typecheck
npm run lint            # ESLint 9 flat config with jsx-a11y and import order, zero warnings
npm run format:check    # Prettier
npm run knip            # unused files, exports and dependencies
npm test                # Vitest
npm run build
npm run test:e2e        # Playwright against the production build on an in-memory PGlite
```

- **Pure logic** (`src/lib/__tests__`): URL query parsing and serialising, filters, sorting, grouping, sort keys, the optimistic reducer and board drop placement.
- **Server Actions** (`src/server/actions/__tests__`): the real actions against an in-memory PGlite with the real migrations: create (numbering, validation, workspace checks), update with activity, move between columns, delete and undo, comments, labels. Only the Next.js request and cache APIs are stubbed.
- **Messages** (`src/i18n/__tests__`): key and argument parity across locales.
- **Flows** (`src/features/**/__tests__`, Testing Library and vitest-axe): optimistic status change and rollback, create with `C` and `Cmd`/`Ctrl` + `Enter`, `S` on a hovered issue, `G` sequences, the palette, delete with undo. Server Actions are stubbed as the network boundary.
- **End to end** (`tests/e2e`): create an issue from the palette, move a card on the board by keyboard and reload, switch to German, no horizontal scroll at 375 px, and axe on every page in light and dark mode.

Commit messages are plain sentences in the past tense. lint-staged formats and lints staged files. CI (`.github/workflows/ci.yml`) checks out `eylulg/ui` next to the repository and builds it before `npm ci`, then runs typecheck, lint, format check, knip, tests, build and the end to end suite, plus a gitleaks secret scan.

## Deploy

The target is Vercel with a Neon Postgres database.

Vercel cannot resolve the `file:../ui` dependency, because the library is not part of this repository. Until `@eylulg/ui` is published to npm, deploy from a machine that has both folders, or publish the library first, then change the dependency in `package.json` to `"@eylulg/ui": "^1.0.0"` and remove the library steps from CI. Nothing else in the app changes.

1. Create a Neon project and copy the pooled connection string.
2. Import the repository in Vercel and set the environment variables below.
3. From your machine, with `DATABASE_URL` set to the Neon string, run `npm run db:migrate`.
4. Deploy. `vercel.json` schedules `GET /api/cron/cleanup-demo` every night at 03:00 UTC, which deletes visitor copies older than a day.

| Variable                   | Required | Purpose                                                        |
| -------------------------- | -------- | -------------------------------------------------------------- |
| `DATABASE_URL`             | yes      | Postgres connection string (Neon, pooled). Empty means PGlite. |
| `CRON_SECRET`              | yes      | Vercel sends it as a bearer token to the nightly reset route.  |
| `NEXT_PUBLIC_POSTHOG_KEY`  | no       | Turns on PostHog analytics.                                    |
| `NEXT_PUBLIC_POSTHOG_HOST` | no       | PostHog host, defaults to the EU cloud.                        |
| `PGLITE_DIR`               | no       | Local PGlite folder (default `.pglite`), or `memory`.          |

See `.env.example`.
